Running `10xgraph init --template production` scaffolds a complete, production-ready 10xGraph project. The template generates a working agent with a state class, a tool, input validation, safety hooks, an integrated test suite, evaluation examples, and a 10xgraph.json config ready for deployment. Every file has a clear purpose, and you customize them to build your agent. This page explains what gets created, how each part works, and what every configuration key does.

## How do I generate it?

The most common way to scaffold a production project with authentication and rate limiting:

```bash
10xgraph init --template production --auth jwt --rate-limit redis --yes
```

The command accepts several options:

| Option | Values | Purpose |
|---|---|---|
| `--template` | `quick-start`, `production` | Template to use. Quick-start is minimal; production includes auth, tests, evals and lint. |
| `--auth` | `none`, `jwt`, `custom` | Authentication scheme. Required for production template. |
| `--rate-limit` | `none`, `memory`, `redis` | Rate limiting backend. Required for production template. |
| `--name` | string | Agent name (used in generated files and config). Default: `agent`. |
| `--path` | directory | Where to scaffold the project. Default: current directory. |
| `--yes` | flag | Use the supplied options without interactive prompts. |
| `--non-interactive` | flag | Run without any interactive prompts. |
| `--dry-run` | flag | List files that would be created without writing them. |
| `--force` | flag | Overwrite existing files (including 10xgraph.json). |

Without `--yes` or `--non-interactive`, init presents guided prompts for each option, allowing you to customize the generated project interactively.

## What files does it create?

<FileTree>

- **10xgraph.json** Configuration that the API server and CLI read on every run
- .env.example Environment variable template; copy to .env and fill in your API keys
- .python-version Pin the Python version (3.12 or later)
- .pre-commit-config.yaml Git hooks for formatting, linting, and security checks
- pyproject.toml Project metadata, dependencies, and tool configuration
- graph/ Your agent implementation package (importable as a module)
  - **agent.py** Entry point: builds and compiles your ReactAgent, exports `app`
  - state.py Custom AgentState subclass with domain-specific fields
  - thread_name_generator.py Names threads based on first user message
  - tools/ Tool functions available to your agent
    - weather_tool.py Example tool with retry logic and error handling
  - validators/ Input validation and lifecycle hooks
    - manager.py Registers validators and lifecycle hooks on the callback manager
    - validators.py Prompt-injection validator that guards against malicious input
    - lifecyle.py Lifecycle hooks that respond to graph start, end, errors, interrupts and state changes
- auth/ Custom authentication implementation (only with `--auth custom`)
  - agent_auth.py BaseAuth subclass; implement the `authenticate` method
- evals/ Evaluation sets for testing agent behavior
  - weather_agents_eval.py Example eval set (replace with your test cases)
  - user_simulator_eval.py Example eval using simulated user messages
- tests/ Pytest suite
  - conftest.py Shared test fixtures
  - test_graph_nodes.py Unit tests for graph nodes
  - test_catalog_tools.py Tests for tool definitions and execution

</FileTree>

The `auth/` folder is created only when you choose `--auth custom`. The `lifecyle.py` spelling (not "lifecycle") matches the generated template. When you run init without the `--auth` flag in quick-start mode, the auth folder is omitted.

## Project structure: how it all fits together

The generated project organizes your agent code, configuration, and tests so that the 10xGraph API server can load and run your agent. Here is how the pieces connect:

**Entry point:** `graph/agent.py` imports your state class, tools, and validators, then builds and compiles a `ReactAgent` into `app`, which is exported. The `app` variable is a `CompiledGraph` (a runnable agent). The `10xgraph.json` config tells the API server where to find this: `"agent": "graph.agent:app"`.

**Configuration:** `10xgraph.json` points to your agent, specifies auth options, rate limits, checkpointing strategy, and optional features. The API server reads this file on startup and configures itself accordingly.

**State and messages:** `graph/state.py` defines an `AgentState` subclass that holds the agent's working state. Your custom fields appear here. During execution, the graph accumulates messages and state changes; checkpointers save them.

**Tools:** `graph/tools/` holds tool functions. Each tool is a Python function decorated with `@tool` or passed to the Agent constructor. Tools can declare injected parameters like `state`, `emit`, and `tool_call_id` to access context.

**Validation and lifecycle:** `graph/validators/` includes a prompt-injection guard (active by default) and lifecycle hooks that respond to graph events. Hooks let you hydrate state at the start, clean up at the end, or respond to errors and interrupts.

**Testing:** `tests/` includes unit tests for your graph nodes and tools. Run them with `10xgraph test`. The suite is pre-wired with pytest fixtures and coverage reporting.

**Evaluation:** `evals/` holds evaluation sets (test cases with expected outputs). Run them with `10xgraph eval`. Evals measure agent quality; unit tests verify correctness.

## Understanding each generated file

### graph/agent.py

This is your agent's entry point. It imports all components, builds a `ReactAgent`, and compiles it to a `CompiledGraph`:

```python title="graph/agent.py"
from tenxgraph.core.state import MessageContextManager
from tenxgraph.prebuilt.agent import ReactAgent
from tenxgraph.storage.checkpointer import InMemoryCheckpointer
from dotenv import load_dotenv

from graph.state import WeatherState
from graph.tools.weather_tool import get_weather
from graph.validators.manager import callback_manager


load_dotenv()

checkpointer = InMemoryCheckpointer()

context_manager = MessageContextManager(
    max_messages=20,  # last 20 user messages will be kept in context
    remove_tool_msgs=True,
)

react_agent = ReactAgent(
    state=WeatherState(),
    model="google/gemini-2.5-flash",
    provider="google",
    system_prompt=[...],
    trim_context=True,
    tools=[get_weather],
    context_manager=context_manager,
)

app = react_agent.compile(
    checkpointer=checkpointer,
    callback_manager=callback_manager,
)
```

The `ReactAgent` orchestrates your agent's reasoning loop: it calls your LLM, interprets tool calls, executes tools, and updates state. The `compile()` call wraps it in a `CompiledGraph` that the API server can run.

**Before deploying:** Replace `InMemoryCheckpointer` with a durable checkpointer (SQLite or Postgres+Redis) so your agent's state persists across restarts. See [Checkpointing and threads](/docs/concepts/checkpointing-and-threads).

### graph/state.py

A custom state class inheriting from `AgentState`:

```python title="graph/state.py"
from tenxgraph.core import AgentState


class WeatherState(AgentState):
    user_location: str = ""
```

Add any fields your agent needs. These fields persist in the checkpoint and are available to your tools and system prompt. Use type hints so the state is introspectable.

### graph/tools/weather_tool.py

Example tool that shows how to use injected parameters (`tool_call_id`, `state`, `emit`):

```python title="graph/tools/weather_tool.py"
from tenxgraph.core.state.stream_emitter import StreamEmitter
from graph.state import WeatherState

MAX_RETRIES = 3

def get_weather(
    location: str,
    tool_call_id: str | None = None,
    state: WeatherState | None = None,
    emit: StreamEmitter | None = None,
) -> str:
    """Get the current weather for a specific location."""
    if tool_call_id:
        logger.info(f"Tool call ID: {tool_call_id}")
    if state and hasattr(state, "context"):
        logger.info(f"Number of messages: {len(state.context)}")
    if emit:
        emit.progress("Fetching weather data...")
    
    for i in range(MAX_RETRIES):
        try:
            return call_weather_api(location)
        except Exception as e:
            logger.error(f"Attempt {i + 1} failed: {e}")
            if emit:
                emit.progress(f"Attempt {i + 1} failed, retrying...")
    
    return f"Sorry, I couldn't fetch the weather for {location}."
```

Tools can be async (use `async def`). To add your own tools, create new files in `graph/tools/` and pass them to `ReactAgent(..., tools=[...])`.

### graph/validators/validators.py

A prompt-injection guard that rejects suspicious input:

```python title="graph/validators/validators.py"
from tenxgraph.utils.validators import PromptInjectionValidator

prompt_validator = PromptInjectionValidator(
    strict_mode=True,
    max_length=1000,
    blocked_patterns=[],
    suspicious_keywords=[
        "ignore previous",
        "forget previous",
        "disregard previous",
        "bypass",
        "circumvent",
        "override",
        "disable",
        "remove restrictions",
        "token",
        "coupon",
        "free",
    ],
)
```

Edit `suspicious_keywords` for your domain. The example list is tuned for a weather agent; you may need to add or remove words so legitimate input is not blocked.

### graph/validators/manager.py

Registers validators and lifecycle hooks:

```python title="graph/validators/manager.py"
from tenxgraph.utils.callbacks import CallbackManager

from .lifecyle import AgentLifecycleHook
from .validators import prompt_validator

callback_manager = CallbackManager()
callback_manager.register_input_validator(prompt_validator)
callback_manager.register_lifecycle_hook(AgentLifecycleHook())
```

The `CallbackManager` is passed to your agent at compile time and invokes validators and hooks at the appropriate moments. To add more validators or hooks, create them in separate files and register them here.

### graph/validators/lifecyle.py

Lifecycle hooks respond to graph events (start, end, error, interrupt, checkpoint):

```python title="graph/validators/lifecyle.py"
from tenxgraph.utils.callbacks import GraphLifecycleHook, GraphLifecycleContext
from graph.state import WeatherState

class AgentLifecycleHook(GraphLifecycleHook[WeatherState]):
    async def on_graph_start(
        self, context: GraphLifecycleContext, state: WeatherState
    ) -> WeatherState | None:
        """Hydrate state from auth context before the agent runs."""
        return state

    async def on_graph_end(
        self, context: GraphLifecycleContext, final_state: WeatherState,
        messages: list, total_steps: int
    ) -> WeatherState | None:
        """Called after successful completion; return modified state or None."""
        return None

    async def on_graph_error(
        self, context: GraphLifecycleContext, error: Exception,
        partial_state: WeatherState, messages: list, step: int, node_name: str
    ) -> tuple[WeatherState, str] | None:
        """Called on unhandled error; return (modified_state, error_message) or None."""
        return None
```

The template provides stub implementations for all hook methods. Override them to respond to events (for example, logging, cleanup, state augmentation).

### graph/thread_name_generator.py

Generates human-readable names for threads (conversation sessions):

```python title="graph/thread_name_generator.py"
from tenxgraph_api import ThreadNameGenerator

class MyNameGenerator(ThreadNameGenerator):
    async def generate_name(self, messages: list[str]) -> str:
        # TODO: Implement logic to generate thread name based on messages
        return "MyCustomThreadName"
```

The `messages` parameter is a list of message strings from the user's first turn. Use them to derive a name (e.g., extract a topic). The name appears in thread listings and logs.

### auth/agent_auth.py

Custom authentication (only with `--auth custom`):

```python title="auth/agent_auth.py"
from tenxgraph_api import BaseAuth
from fastapi import HTTPException, Request, Response
from fastapi.security import HTTPAuthorizationCredentials

class AgentAuth(BaseAuth):
    """Verify the caller and return who they are."""

    def authenticate(
        self,
        request: Request,
        response: Response,
        credential: HTTPAuthorizationCredentials,
    ) -> dict[str, Any] | None:
        if credential is None:
            raise HTTPException(status_code=401, detail="Missing credentials")
        
        # Verify the bearer token (e.g., with your identity provider):
        # claims = verify_token(credential.credentials)
        # return {"user_id": claims["sub"], "roles": claims.get("roles", [])}
        
        raise HTTPException(status_code=401, detail="Not configured")
```

The `authenticate` method receives a request and credential, verifies them, and returns a dict with at least `"user_id"`. The `user_id` becomes the thread owner, so it must come from a verified credential. Optional `roles` or `scopes` feed the authorization backend.

### evals/ and tests/

**Evals** (`evals/weather_agents_eval.py` and `user_simulator_eval.py`) define evaluation test cases. Each file exports an `eval_set` that specifies inputs, expected behaviors, and scoring criteria. Run with `10xgraph eval`.

**Tests** (`tests/test_graph_nodes.py`, `test_catalog_tools.py`, `conftest.py`) are Pytest tests. They use fixtures from `conftest.py` to instantiate your agent and test nodes and tools in isolation. Run with `10xgraph test`. The suite is pre-configured for coverage reporting and linting.

### .env.example

A template for environment variables. Copy to `.env` and fill in your API keys:

```bash title=".env.example"
# App Config
APP_NAME="agent"
APP_VERSION="0.1.0"
MODE="production"
LOG_LEVEL="INFO"
IS_DEBUG="false"

# CORS and Security
ORIGINS="*"
ALLOWED_HOST="*"
DOCS_PATH=""
REDOCS_PATH=""

# Request Limits
MAX_REQUEST_SIZE=10485760  # 10MB

# Security Headers
SECURITY_HEADERS_ENABLED="true"
HSTS_ENABLED="true"

# Snowflake ID Generation
SNOWFLAKE_EPOCH=1609459200000
SNOWFLAKE_NODE_ID=1
SNOWFLAKE_WORKER_ID=2

# Sentry (error tracking)
SENTRY_DSN=""

# Redis (only if --rate-limit redis)
REDIS_URL=""

# JWT (only if --auth jwt)
JWT_SECRET_KEY=""
JWT_ALGORITHM="HS256"

# API Keys
GOOGLE_API_KEY=""
```

The template includes conditional blocks (`##[IF_REDIS]##`, `##[IF_JWT]##`) that are expanded when you choose auth or rate-limit options. In production, never commit `.env`; load it from a secrets manager.

### pyproject.toml

Project metadata, dependencies, and tool configuration:

```toml title="pyproject.toml"
[project]
name = "my-agent"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
    "10xgraph",
    "10xgraph-api",
    "google-genai",
]

[project.optional-dependencies]
test = [
    "pytest",
    "pytest-asyncio",
    "pytest-cov",
    "pytest-env",
]

[tool.ruff]
line-length = 100
target-version = "py312"
lint.select = ["E", "W", "F", "PL", "I", "B", ...]

[tool.pytest.ini_options]
testpaths = ["tests"]
pythonpath = ["."]
addopts = [
    "--cov=graph", "--cov-report=html", "--cov-fail-under=0", "-v"
]
```

- Requires Python 3.12 or later.
- Pins `10xgraph` (core) and `10xgraph-api` (server/CLI).
- Includes your LLM provider's SDK (e.g., `google-genai`, `openai`, `anthropic`).
- Configures Ruff for code formatting and linting.
- Configures Pytest with coverage targets.

Run `pip install -e ".[test]"` in development to install with test extras.

## Understanding 10xgraph.json

The config file tells the API server how to load your agent, handle authentication, rate limit requests, and checkpoint state:

```json title="10xgraph.json"
{
  "agent": "graph.agent:app",
  "env": ".env",
  "auth": "jwt",
  "thread_name_generator": "graph.thread_name_generator:MyNameGenerator",
  "ag_ui": { "enabled": false },
  "authorization": "ownership",
  "injectq": "graph.agent:container",
  "rate_limit": {
    "enabled": true,
    "backend": "redis",
    "redis": {
      "url": "${REDIS_URL}",
      "prefix": "10xgraph:rate-limit"
    },
    "requests": 100,
    "window": 60,
    "by": "user",
    "trusted_proxy_headers": true,
    "trusted_proxy_hops": 1,
    "fail_open": false,
    "exclude_paths": ["/ping", "/docs", "/redoc", "/openapi.json"]
  },
  "test": {
    "path": "tests",
    "coverage": true,
    "coverage_threshold": 70
  },
  "evaluation": {
    "directory": "evals",
    "output_dir": "eval_reports",
    "threshold": 0.75,
    "parallel": false,
    "max_concurrency": 4,
    "timestamp_files": true
  }
}
```

| Key | Type | Purpose |
|---|---|---|
| `agent` | string | `module:variable` path to your compiled graph (required). |
| `env` | string | Path to `.env` file to load before starting. |
| `auth` | `null`, string, or object | `null` for no auth, `"jwt"` for JWT (needs `JWT_SECRET_KEY` env var), or `{"method": "custom", "path": "module:class"}` for custom auth. |
| `authorization` | string | Authorization backend: `"ownership"` (thread owner only), `"allow_all"`, `"default"`, or a custom backend path. |
| `thread_name_generator` | string | `module:class` of a `ThreadNameGenerator` subclass. |
| `ag_ui` | object | AG-UI (CopilotKit) endpoint config. `{"enabled": false}` disables it; set `enabled: true` to activate. |
| `injectq` | string | `module:variable` of an InjectQ DI container (optional). |
| `remote_tools` | array | List of remote tools callable from client code (empty by default). |
| `rate_limit` | object | Rate limiting config (see below). |
| `test` | object | Test config: `path`, `coverage` (bool), `coverage_threshold` (percent). |
| `evaluation` | object | Eval config: `directory`, `output_dir`, `threshold` (score), `parallel` (bool), `max_concurrency`, `timestamp_files` (bool). |

### Rate limit configuration

When `rate_limit.enabled` is true, the API server enforces request limits:

| Key | Values | Purpose |
|---|---|---|
| `backend` | `"memory"`, `"redis"`, `"custom"` | Where to store request counts. Memory is in-process; Redis is shared across workers. |
| `requests` | number | Max requests per window (default 100). |
| `window` | seconds | Time window in seconds (default 60). |
| `by` | `"ip"`, `"user"`, `"global"` | Limit per client IP, authenticated user, or all clients combined. |
| `trusted_proxy_headers` | boolean | Honor `X-Forwarded-For` from proxies (set true behind a reverse proxy). |
| `trusted_proxy_hops` | number | How many hops to trust in `X-Forwarded-For` (default 1). |
| `exclude_paths` | array | Paths not counted against the limit (e.g., `/ping`, `/docs`). |
| `fail_open` | boolean | On backend error: true = allow requests; false = deny (default false). |
| `redis` | object | If backend is `redis`: `{ "url": "redis://...", "prefix": "..." }`. |

The template uses `"by": "user"` when auth is configured (JWT or custom), because it limits per authenticated identity. Change to `"by": "ip"` to limit per client IP.

## Important notes before deploying

<Callout type="warning" title="The injectq key has a bug in the template">

The generated `10xgraph.json` includes `"injectq": "graph.agent:container"`, but `graph/agent.py` does not define a `container` variable. The server will raise an error at startup: `AttributeError: module 'graph.agent' has no attribute 'container'`.

To fix this, either:

1. **Delete the key** from `10xgraph.json` if you do not use dependency injection yet.
2. **Add the container** to `graph/agent.py`:

```python title="graph/agent.py"
from injectq import InjectQ

container = InjectQ.get_instance()
```

When you are ready to use dependency injection, populate the container with your dependencies (e.g., database connections, config objects) and reference them in your tools and nodes.

</Callout>

<Callout type="tip" title="Checkpointing in production">

The template uses `InMemoryCheckpointer`, which stores state in memory and is lost when the server restarts. Before deploying, switch to a durable checkpointer:

- SQLite for single-machine deployments
- Postgres + Redis for distributed deployments

See [Set up checkpointing](/docs/guides/set-up-checkpointing) for detailed configuration.

</Callout>

<Callout type="note" title="Customize security settings">

The `.env.example` defaults `ORIGINS="*"` and `ALLOWED_HOST="*"`, which allow requests from any domain. Before production, restrict these to your actual client domains and set `DOCS_PATH=""` to disable API documentation endpoints.

</Callout>
