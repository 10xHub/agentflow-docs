    How PgCheckpointer works

    In shortThe internal mechanisms of PgCheckpointer's two-layer storage model, the write path, read path, and optimistic concurrency control for thread state.

    PgCheckpointer implements a two-layer storage model: a durable layer in PostgreSQL with full versioned history, and a hot cache layer in Redis with TTL-controlled entries. Understanding how state flows through these layers is essential for production deployment and debugging concurrency issues.

    The two-layer model

    Layer Purpose Lifetime Guarantees
    Hot cache Fast reads, reduces Postgres load TTL (default 86400 seconds / 24 hours) Best-effort; failures are silent
    Durable storage Persistent, versioned history Until thread is deleted Atomic, transactional, authoritative

    PostgreSQL is the source of truth. Redis is expendable: if it crashes or the cache entry expires, the next read simply falls back to Postgres. Conversely, losing the Redis cache does not lose data.

    The write path: durable first, then cache

    When a graph completes a node and needs to checkpoint state, PgCheckpointer.aput_checkpoint() executes two sequential operations:

    1. Durable write to PostgreSQL

    State is written in a single database transaction that:

    1. Acquires a per-thread row lock to serialize writes (preventing lost updates when multiple workers run the same thread concurrently)
    2. Performs an optimistic version check: reads the current version from the states table, compares it to the version the run read at the start, and raises StaleStateError if another run committed in the meantime
    3. If the check passes, inserts a new row with version = current_version + 1 and the serialized state data
    4. Inserts any new messages into the messages table
    5. Prunes historical versions older than state_history_limit (default 20 rows)
    6. Commits the transaction

    If PostgreSQL fails before commit, the transaction is rolled back and no state is persisted. The run’s thread is left unchanged.

    2. Cache refresh to Redis

    After PostgreSQL commits, the same state is written to Redis under the key state_cache:{thread_id}:{user_id} with the configured TTL. This cache write is atomic via Lua script and includes a version guard: the script compares the incoming version to any existing cached version and only writes if the new version is equal or newer. This prevents a stale run from overwriting a newer cached state with a Lua script atomically.

    If the Redis write fails, the failure is logged and ignored. The durable state is safe in PostgreSQL, and the next read will fall back to Postgres and refresh the cache.

    Write sequence guarantees

    The PostgreSQL-first ordering ensures the cache never holds state that is not durable. If a crash occurs between the Postgres commit and the Redis write, the Redis cache remains stale (or empty), but the durable state is safe. The next read will detect the cache miss and fetch from Postgres.

    The read path: cache-aware with atomic fallback

    At the start of a run, PgCheckpointer.aget_state_cache() retrieves the thread’s latest state:

    1. Redis hit: Read state_cache:{thread_id}:{user_id} from Redis. Extract the embedded version number (stored as __checkpoint_version__ in the cached JSON). Restore it into config['_checkpoint_version'] so a subsequent write can use it for the version check. Return the deserialized state.

    2. Redis miss or error: Execute a Postgres read:

      • Query SELECT version, state_data FROM states WHERE thread_id = ? ORDER BY version DESC LIMIT 1
      • Deserialize the state and extract the version
      • Populate config['_checkpoint_version'] with this version
      • Return the state

    3. Thread not found in Postgres: Return None. The graph will initialize a fresh AgentState and use the incoming messages (if any) to populate it.

    4. Cache refreshed on miss: If the Postgres read succeeded, immediately write the result back to the Redis cache (with TTL) so the next call to this thread hits the cache.

    This two-stage read minimizes Postgres load in the common case (cache hits) while guaranteeing correctness (the version from either cache or Postgres is used for the next write’s compare-and-swap).

    Versions and optimistic concurrency control

    Every call to aput_checkpoint() or aput_state() performs a compare-and-swap:

    1. The run reads a thread’s state at the start and records its version in config['_checkpoint_version']
    2. The run executes its graph
    3. At the end, the write checks if version still matches the current row’s version in Postgres
    4. If another run committed a new version in the meantime, the write raises StaleStateError instead of updating

    The SQL check is enforced via a WHERE clause in the insert’s lock condition. If the check fails:

    • The transaction is rolled back (no state is persisted)
    • The cached entry is invalidated (dropped from Redis) to prevent the thread from staying stuck on stale data
    • StaleStateError is raised to the caller

    This prevents lost updates: each run’s writes are serialized by version number, and concurrent runs that started from the same version cannot both commit.

    Example: three concurrent runs

    Run A succeeds. Runs B and C both fail because they started from v=0 but A already advanced to v=1. Their cache entries are dropped so they do not poison the next read. The calling code can retry them if needed.

    History pruning and bounded growth

    By default, PgCheckpointer keeps 20 state snapshots per thread (state_history_limit=20). After each successful write, rows older than this limit are deleted:

    This prevents the states table from growing indefinitely. The 20-row window is enough for debugging the recent execution history but not an audit log. If you need to preserve all history, export it before it is pruned, or increase state_history_limit (at the cost of more Postgres storage).

    Messages are stored separately in the messages table and are not automatically pruned by version limits (only by explicit deletion or thread cleanup).

    Database schema and table structure

    The PgCheckpointer.asetup() method creates these tables (in the specified schema, default public):

    Table Purpose
    threads Thread metadata: thread_id, user_id, name, created_at, metadata
    states Versioned state snapshots: thread_id, user_id, version (primary), state_data (JSON), created_at
    messages Message history: thread_id, message_id, message_data (JSON), created_at
    tool_executions Tool call ledger for replay safety: thread_id, tool_call_id, status, result
    Schema version table Tracks migrations

    The states table has a unique index on (thread_id, user_id, version) to enforce one version per thread. Writes acquire a row lock on the thread’s metadata row in threads to serialize concurrent writers.

    User isolation and scoping

    By default, enforce_user_isolation=True. Every query to states includes a WHERE user_id = ? clause scoped to the user_id in the config dict. This prevents one user from reading or writing another user’s thread, even if they know the thread_id.

    PgCheckpointer raises a ValueError at construction if user_id is missing from the config during a read or write. The API server fills user_id from the authenticated request (or sets it to "anonymous" if no auth is configured). Turn off isolation only for single-tenant deployments where all threads are logically shared.

    Cache invalidation on conflict

    When a write fails the optimistic version check, PgCheckpointer immediately calls _invalidate_state_cache() to drop the cached entry:

    This prevents a poisoned cache: if Run A loses its race and reads the cached state that Run B wrote (which was built on a newer version), Run A’s next write will again fail because it is trying to commit the older version. By dropping the cache, Run A’s next read will fetch from Postgres and get the latest version, allowing it to retry successfully.

    Frequently asked questions

    What happens when the Redis cache expires or Redis restarts?
    Nothing is lost. PostgreSQL holds the authoritative state, so the next read misses the cache, loads the latest version from PostgreSQL and writes it back to Redis. The cache TTL defaults to 86400 seconds (24 hours).
    How much history does PgCheckpointer keep?
    It keeps the 20 most recent state snapshots per thread by default and prunes older ones on every durable write. Change this with the state_history_limit argument. Messages are stored in their own table.
    What happens when two runs write to the same thread at the same time?
    PgCheckpointer uses optimistic concurrency control. Each write performs a version check. If another run committed a new version since this run started, the write fails with StaleStateError and the cache is invalidated to prevent the thread from staying stuck on stale data.
